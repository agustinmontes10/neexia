## Commands

- `npm run dev` — start the dev server (Turbopack). Default port is 3000; if another local project already holds it, Next.js auto-selects the next free port (e.g. 3001) and prints the actual URL in the terminal — check the log rather than assuming 3000.
- `npm run build` — production build.
- `npm run start` — serve the production build.
- `npm run lint` — ESLint (flat config: `eslint-config-next` core-web-vitals + typescript rules).
- `npx tsc --noEmit` — type-check; there is no dedicated `typecheck` script.
- No test runner is configured in this project.

## Architecture

This is a Next.js App Router marketing site for Neexia (an AI agency), replicated from a Claude Design mock ("Landing page para Neexia", fetched via the design MCP). The main experience is the single-page landing at `/`; the other routes are per-service detail pages at `/servicios/[slug]` and per-project detail pages at `/casos/[slug]`.

- `app/page.tsx` composes the landing page by stacking section components in order: `Nav`, `Hero`, `Logos`, `Servicios`, `Proceso`, `Casos`, `CtaFinal`, `Footer` (all in `app/components/`). The root wrapper here must **not** get `overflow-x-hidden` (or any non-`visible` overflow) — it becomes the nearest scroll container and silently breaks `position: sticky` for every descendant. Scope any overflow-clipping needs (e.g. decorative bleed) to the individual component instead, as `Hero.tsx` already does.
- `ToolsBanner.tsx` (rendered inside `Hero.tsx`, below the CTA buttons, full-width) has two independent layouts, not one responsive one: `DesktopDiagram` (`hidden sm:block`) draws six tool icons at staggered heights (per-node `x`/`y` authored by hand in a `VB_W`×`VB_H` viewBox coordinate space) with smooth SVG bezier `<path>`s curving down into a central brand-gradient hub, each with an `<animateMotion>`-driven dot flowing along the exact same `d` path — deliberately not CSS, since arbitrary curves can't be animated with the `flow-dot-x`/`flow-dot-y` keyframes used elsewhere. `MobileStack` (`sm:hidden`) is a plain vertical chain (reusing the straight-line `flow-dot-y` keyframe) rather than a scaled-down version of the curved diagram, matching the "fancy on desktop, simple static-ish fallback on mobile" precedent `Proceso.tsx` already established. Icon positions are percentages of the viewBox so the whole desktop diagram scales with a single `aspect-[8/3]` container instead of breakpoint-specific coordinates. The icon SVG markup in the `ICONS` map is real brand artwork copied verbatim from the Iconify `logos`/`skill-icons` collections and vscode-icons' `file-type-excel` (extracted once via a scratch script, not an installed dependency — see git history if the source needs re-checking) and rendered via `dangerouslySetInnerHTML`; gradient `<defs>` ids in that markup are placeholders (`tb-wa-1`, `tb-ig-2`, etc.) that `ToolIcon` rewrites per-instance with `useId()` — required because the desktop and mobile layouts both render the same icon at the same time (one hidden via CSS, not unmounted), so a hardcoded id would collide and silently break the gradient fill on whichever copy loses. A horizontal single-row "spine" and, before that, a radial hub-and-spoke circle and a horizontal marquee were each replaced outright rather than iterated on — check git history before assuming the current shape is final if asked to redesign this again. `Hero.tsx`'s `WorkflowDemo` ("Ejemplos, en vivo") is currently commented out (import + JSX) rather than deleted, pending a decision on whether to bring it back.
- Copy/content is centralized in `app/lib/landing-data.ts` as typed arrays (`services`, `steps`, `cases`, `logos`). Edit content there, not inside the section components.
- `app/components/ServiceIcon.tsx` renders the small line-art icons (`diagnostic`/`automation`/`agents`/`chat`/`web`) switched on the `Service.icon` field from `landing-data.ts`; the same field also selects which bespoke animated visual `app/components/ServiceVisual.tsx` renders.
- `Servicios.tsx` is a tabbed section (pill tabs, one per service) that auto-advances on a timer and pauses on hover; `ServiceVisual.tsx` holds one hand-built animation per service (report scan, node graph, AI hub, chat skeleton, responsive web frame) rather than a single generic component. Each tab panel has a "Ver más" link to that service's detail page.
- `app/servicios/[slug]/page.tsx` is the per-service detail page, statically generated via `generateStaticParams` from `services[].slug` (`notFound()` for unknown slugs). It reuses `ServiceIcon`/`ServiceVisual` plus the shared `Nav`/`CtaFinal`/`Footer` for visual consistency with the home page. The expanded copy fields on `Service` (`longDescription`, `benefits`, `idealFor`) are currently placeholder text ("— completar") and need a real writing pass before shipping.
- `Proceso.tsx` has a CSS-only animated progress line behind the step numbers (`proceso-fill`/`proceso-step-N`/`proceso-tip-glow` keyframes in `globals.css`) that fills and colors each number in sequence, looping forever. The four `proceso-step-N` keyframes are hardcoded per index and assume `steps.length === 4` — adding/removing a step requires updating both the keyframes and the `STEP_ANIMATIONS` array in `Proceso.tsx`. The effect is desktop-only (`lg:`); below that breakpoint steps just stack with plain static numbers.
- Styling is Tailwind CSS v4 using the CSS-first config in `app/globals.css` (`@theme inline` block) — there is no `tailwind.config.js`. Brand colors are exposed as `--color-brand` / `--color-brand-dark` and consumed via `bg-brand`, `text-brand`, `hover:bg-brand-dark`, etc. Custom keyframe-driven animations (e.g. `check-wave`, `web-resize`, `proceso-fill`) follow the same pattern: define `@keyframes` plus a matching `--animate-*` theme var, then use the generated `animate-*` utility class.
- Nav/CTA links to the landing sections use root-relative hash links (`/#servicios`, `/#proceso`, `/#casos`, `/#contacto`) via `next/link`, not bare `#anchor`s — this is required so they still resolve correctly from `/servicios/[slug]`, not just from `/`. Keep these `id`s in sync with `Nav.tsx` and the CTA links if sections are renamed or reordered.
- `Casos.tsx` renders success-story cards as a light bento grid (first case wider on `lg:`) driven by real animated content, not photos: an oversized counting metric, a per-case hand-built SVG/CSS graphic matching that project (`app/components/CaseVisual.tsx`, switched on the `CaseStudy.visual` field: `workflow`/`agentHub`/`webPreview`), a quote, and an initials avatar derived from the client name. This was a deliberate move away from photo-overlay cards since no real client photography exists yet; the `webPreview` visual falls back to a gradient placeholder until `CaseStudy.image` is set to a real screenshot. Each card has a "Ver caso completo" link to that project's detail page.
- `app/casos/[slug]/page.tsx` is the per-project detail page, statically generated via `generateStaticParams` from `cases[].slug` (`notFound()` for unknown slugs), mirroring the structure of `app/servicios/[slug]/page.tsx`: hero (role badge, title, `longDescription`, CTA, big `CaseVisual`), a "Qué hicimos" checklist (`CaseStudy.highlights`), a result card (metric/quote/avatar), and a "Servicios aplicados" row that cross-links to `/servicios/[slug]` via `CaseStudy.relatedServices` (slugs into `services`). `longDescription` and `highlights` are placeholder copy ("— completar") pending a real writing pass.
- Placeholder content still needs real assets: client logos (`Logos.tsx`) and the phone number and social links (LinkedIn/Instagram) in `Footer.tsx` are all stand-ins.
